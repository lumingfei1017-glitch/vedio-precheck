## 3. 这次验证出来的硬规则（最关键）

Wan 3.0 共跑了 10 次（A–J），结论已写进 [plan-audio-block-replace.md](plan-audio-block-replace.md) §2.2：

1. **输出时长 ≤ 参考镜头时长**，用 `floor()`。G（7s，参考 5.5s）发糊，J 同文案改 5s 立刻正常，单变量对照已验证。
2. **参考音频必须同场景**，跨场景会把那个场景带进画面（B 版切到别的镜头）。
3. **文案按 5–5.5 字/秒**，空档会被原句碎片填空（H 版）；太满会赶。
4. **新文案首尾不要与原句一致**，否则模型会顺着上下文复读原句（F 版音频相关度 0.951）。
5. **替换粒度是整镜**，切点必须落在原片硬切（`ffmpeg select='gt(scene,0.3)'`）。镜头中间硬贴会两头姿态错位。
6. Wan 音色优于克隆 TTS，所以 TTS 只在 Wan 失败后兜底，不做主音轨。

失败模式一览：

| 现象 | 原因 |
|---|---|
| 原样复读 | 首尾锚定 + 输出超时长 |
| 发糊吞字 | 输出明显超参考时长 |
| 中途换场景 | 参考音频来自其他场景 |
| 开头多衬字 | 文案太短，模型拿参考音填空 |

## 5. 接口

```text
GET  /api/materials/{id}/shots?refresh=false
POST /api/materials/{id}/shots/replace
     { "start_ms": 78200, "end_ms": 83700, "text": "...", "route": "wan|tts", "dry_run": true }
```

- `dry_run=true` 返回 `duration / char_budget / fit / warnings`，不花钱。
- `dry_run=false` 返回 `job_id`（`kind=shot_replace`），复用 `/api/jobs/{id}` 轮询。
- 任务成功后写回 `material.render_output_path`，`GET /api/materials/{id}/output` 可直接下载。

镜头路由：

| kind | 含义 | route |
|---|---|---|
| `talking_closeup` | 脸占比 ≥6%，嘴清晰 | `wan` |
| `talking_full` | 人脸持续可见但较小 | `wan` |
| `talking_side` | 侧身/转身，嘴不可见 | `tts` |
| `voiceover` | 有人声无人脸 | `tts` |
| `broll` | 无口播 | `keep` |
| `unknown` | 没装 cv2 或待确认 | `manual` |

## 9. 已知问题 / 下一步

按优先级：

1. **M4 兜底链落代码**：方案在 plan §11，顺序是「参数修正重试 → 换 seed 重试一次 → 克隆 TTS 换音轨 → CUT/人工」。
2. **复检未自动化**：现在只有 dry-run 预算，缺 ASR 逐字比对、与参考音频相关度、频谱重心这几项自动判定。
3. **任务队列隔离**：`_executor` 只有 2 个线程，Wan 会占住一个，批量时审核任务会被拖慢；建议渲染单独队列 + 并发上限 2–3。
4. **TTS 产物自动复检未接**：换音轨已完成，但 ASR 字面比对、原违规词残留和频谱/响度还需自动判定。
5. **跨镜头主张未聚合**：一条违规主张可能横跨口播 + 对比镜头，现在按单镜头处理；`edit_plan` 需要 `claim → intervals[]`。
6. **硬字幕**：仍无法擦除，需要 OCR 定位 + 重绘。
7. **前端未做真实浏览器视觉验收**：JS 语法与接口已验证，但没用真实浏览器截图检查布局。
8. **CLI 未跑真实调用**：`scripts/replace_shot.py` 只跑了 dry-run，真实链路是在探针脚本里验证的。
9. **人物/场景一致性未量化**：目前靠抽帧目测，可接人脸相似度或 VLM 判定。

与音色相关的下一步设计见 [plan-speaker-voice-profile.md](plan-speaker-voice-profile.md)：说话人分离、按镜头归属、每人音色档案，以及 Wan 参考音的 fail-open 策略。

## 10. 踩坑速查

- Demucs 会先去 HuggingFace 探测模型定义，不通时静默重试 5 次；必须 `HF_HUB_OFFLINE=1` 并预置 `TORCH_HOME`。
- `afade` 必须在 `adelay` 之前，否则整段新配音被淡成静音。
- `amix` 要显式 `normalize=0`。
- 立体声 `adelay` 要写 `ms|ms`。
- OpenCV 5 移除了 `CascadeClassifier`，必须锁 `<5`，否则镜头全判 `unknown`。
- mp3 有编码前置延迟，中间态统一用 wav。

- `app/edit.py`：新增 `_align_replace_ops_to_shots()`；跨镜区间先判路由，
  只有走 Wan 才按镜头拆，TTS 跨切点不拆也不裁区间。
- `build_edit_plan()` 输出 `route_counts`，前端镜头面板显示 Wan/TTS 数量与理由。
- 短镜补齐：`_merged_short_span()` 把 <2s 的替换区间并入相邻口播镜到 2–4s，
  但必须先过 `scene <= MERGE_SCENE_SCORE_MAX`（默认 0.40）的画面闸门，
  合并后按 4.0–6.5 字/秒校验文案密度。实测只有约 7% 的切点够软。
- Wan 的 `duration` 只收 2–30 整数秒，所以回贴必须等长：`build_splice_graph()`
  会把短于槽位的生成片段用末帧冻结 + 静音补齐，再 `trim` 到槽位；返回 `padded_ms`。

所以「违规点很短」不等于替换区间短——10 条能对齐的违规点里有 6 条跨 2–4 个镜头。

## 13. 语义粒度与删段上限（2026-11-22）

起因：`1f584e813a65`（90s）被一条语义事件带着 5 条视觉事件串成 **43 秒连续删段**，
等于删掉半条片子，人工修改成本高于重剪。

三处改动：

1. **提示词按平台判例校准**：171 条真实判例里 169 条是「夸大功效/虚假塑身效果」，
   平台处置是「请修改」而非「删除整段」。口播类违规默认输出可直接口播的改写台词
   （WAN_LIPSYNC / TTS_SUBTITLE，A/C 类），只有画面本身违规（假道具、分屏对比、
   重影、局部特写）才用 CUT_BROLL。事件证据跨度限制 8 秒。
2. **删段按证据簇拆分**：`_split_cut_ops_by_evidence()`，间隔 >1.5s 或跨度 >8s 就断开。
3. **删段长度设上限**：`_merge_cut_ops()` 不再把多段串成超长块；
   `_cap_oversize_cuts()` 把超过 `min(12s, 30% 片长)` 的删段转人工。

同一条素材复测：43s 单块 → 2 条改写（各约 5s）+ 1 条 7.3s 删段 + 2 条待人工确认，
自动删除量从 43s 降到 7.3s。

注意：提示词变更后，历史审核结果需要重新跑一次 `/materials/{id}/review` 才会更新。

## 14. 视觉事件时间定位（2026-11-22）

问题：`VIS-BRAND` 报 22.5–28.1s，实际 Gucci 双 G 内衬在 **25s 和 33s 各出现一次**。
粗筛每 5.6 秒一帧，事件窗口直接等于整个采样桶（±2.8s），既不准也只覆盖一处。

改动：`review_visual()` 结束后对每个视觉事件做一次密集复核。

- 以事件为中心 ±12 秒、1 秒步长抽 24 帧，按**规则特征**而不是模型描述去问
  （描述会把"背景老花"说成"塑身衣内侧"，照抄会定位回错误位置）；
- 返回所有命中片段，而不是只取一处；
- 复核没复现的事件**不丢弃**，保留并在 reason 里标注"时间以抽样帧为准"；
- 复核调用失败时保留原事件不动。

实测同一条素材：`[(25.3, 26.3), (33.3, 34.3)]`，与人工核对一致。
代价是每个视觉事件多一次多图调用，约 15 秒。

配置：`VISUAL_RELOCALIZE_ENABLED`、`VISUAL_RELOCALIZE_RADIUS_MS`、
`VISUAL_RELOCALIZE_STEP_MS`、`VISUAL_RELOCALIZE_MAX_FRAMES`。

## 15. 文案时长硬约束（2026-11-22）

问题：`5.5s → 7.3s 超时长` 的建议只是标了警告，提交照样会跑 Wan，生成时必然吞字糊音。

三层拦截：

1. 改写提示词按 target 给出 `max_chars = 原时长 × 5.0 字/秒`，要求绝不超；
2. `_over_budget()` 判定超长的，自动再压一次（`strict=True`，指令为"压到 max_chars 以内"）；
3. `plan_replace()` 兜底：超过 `时长 × 5.8 字/秒` 直接拒绝提交，报错里写明建议字数和上限。

实测：那条 52 字的产后口播被拒（约 10.4s / 容量 5s）；重新改写后输出 25 字、约 5.0s，
可以正常提交。115 项测试通过。

注意：库里已有的旧建议仍是超长文案，需要点"刷新建议"或重跑审核才会更新。

语速口径已统一（2026-11-22）：估算、文案预算、前端提示统一按 **5.0 字/秒**，
硬拒绝阈值 **5.8 字/秒**。配置项 `SPEECH_CHARS_PER_SECOND` / `SPEECH_MAX_CHARS_PER_SECOND`。
5.5 秒镜头现在显示"建议 25 字、上限 29 字"，52 字的旧文案会被判为约 10.4 秒。

## 16. 视觉删段的置信度门槛与冲突裁决（2026-11-22）

背景：同一条素材前后两次跑，视觉规则名在 `VIS-BODY-COMPARISON` 和
`VIS-EXTREME-STRETCH` 之间漂移，同一段"穿塑身衣/拉拉链"被当成暴力按压，导致
6–7 秒的正常画面被删。逐帧核对后确认是误报。

两条规则：

1. 视觉建议置信度 < 0.8，或判据里含"密集复核未在该时段复现"，**不自动删段**，转人工。
2. 视觉删段与口播改写重叠时按置信度裁决：
   - 视觉 ≥ 0.85 且口播 < 0.95 → **删段优先**（画面违规改写修不了）
   - 其余组合 → **改写优先**，删段缩到不重叠的部分

实测这条素材：`2 段删段优先、0 段改写优先`，自动删段 20.05s → 18.06s，
两处误报（49.9s、66.6s）从"删 6–7 秒"变成"改写 5.6/7.4 秒"。

注意：曾尝试"改写一律优先"，实测会把 84.3–89.9 的"没穿/穿了"分屏留下来
（改写只动音轨），已回退为按置信度裁决。

## 16. 容量计算的三处修正（2026-11-22）

`_max_chars` 的 bug：写死 5.5 字/秒，且用原始时长而不是 Wan 整数生成时长，
导致给改写 Agent 的预算偏高。已改为 `floor(时长) × 5.0`。

另外两处不加调用成本的改进：

1. **备选复用**：主文案超容量时，从 `alternatives` 里挑"最长且装得下"的一条。
   加了 60% 下限——太短的备选会丢卖点，宁可走压缩重试。
2. **大尾巴向上取整**：`planned_duration()` 在 `ceil` 只比参考长 ≤6% 时取 `ceil`，
   否则仍 `floor`。4.92s 槽位从"生成 4s / 25 字容量 20"变成"生成 5s / 容量 25"，
   超出部分由 `splice` 裁回槽位。D 版实测 6.97→7 只超 0.4%，可用。

`validate_generated_duration` 的容差同步放宽为 `参考 × 1.06 + 80ms`，
超过仍拒绝回贴。

## 16. 只保留 Wan 纯口播改写（2026-11-22）

其余（画面问题、短镜、侧身/画外音、文案装不下）全部转人工，由人在剪映精修。

- `TTS_ROUTE_ENABLED` 默认 `false`：路由为 tts 的替换单元直接转 manual。
- `AUTO_CUT_ENABLED` 默认 `false`：所有删段 finding 只进工单，不自动剪。
- `BATCH_RENDER_ENABLED` 默认 `false`：`/apply?dry_run=false` 返回 409。
- `SHOT_TTS_FALLBACK_ENABLED` 默认改为 `false`：Wan 失败不再静默落 TTS。
- 新增 `/materials/{id}/worklist.md` 与 `/worklist.srt`：人工清单 + 可导入剪映的标记轨，
  时间码基于原始视频，工作台不删段、不重排。
- 工单的"可自动改写"条目直接取 `build_edit_plan` 里 route=wan 的替换单元，避免与计划不一致。

连带影响：短镜（<2s）和无脸/侧身镜头不再有 TTS 兜底，自动化率会下降，

## 17. Wan 批量执行（2026-11-23）

"生成修改版"改为真正的 Wan 批处理：逐镜调用 `replace_shot`，能改的改，不能改的保留原样。

判定顺序（`_wan_preflight`，不合格不调用，省一次 4 分钟）：

1. 镜头 ≥ 2s（Wan duration 下限）；
2. 生成时长 ≤ 参考镜头；
3. 文案字数 ≤ `duration × 5.8`；
4. 新文案非空；
5. 首/尾 5 字不与原句相同（防复读）；
6. 区间已在 `_align_replace_ops_to_shots` 对齐到镜头。

执行策略：

- 顺序执行，每段生成后回贴到 `wan-NN.mp4`，时长由 `build_splice_graph` 补齐，不漂移；
- 任一段失败只记录 `skipped`，其余继续，最终视频里该段保持原样；
- 全部失败时输出原视频副本，`mode=unchanged`；
- 结果返回 `applied` / `skipped`（含原因）供前端与工单使用。

`BATCH_RENDER_ENABLED` 恢复默认 `true`；接口 409 仅在显式关闭时触发。

## 18. 侧身镜放开 + 建议固定两条 + 时长短缩上限（2026-11-23）

1. **侧身镜走 Wan**：`decide_route()` 去掉 `talking_side -> tts`，侧身镜头只要 ≥2s
   且覆盖率达标就整镜重生成。实测 `8ec4d183b4bb` 的 Wan 单元从 1 个变成 3 个。
2. **建议固定两条**：`_parse_rewrite` 最终只保留 `alternatives[:1]`，

3. **时长短缩不超过 20%**：
   - target 新增 `min_chars = 原时长 × 5.0 × 0.8`；
   - `_off_budget()` 返回 over / under，两个方向各触发一次重写；
   - 执行前 `_wan_preflight()` 再兜一层：字数 < 原时长 × 4.0 直接跳过并保留原样。

实测同一条 4.5s 口播：原来给 13 字（2.6s，-42%），现在给 20 字（约 4.2s，-7%），
备选 1 条。

## 19. 审核意见 API 接入（2026-11-24）

平台提供内网只读接口 `http://192.168.31.76:8011/api/audits`，返回千川全账户的
拒审 / 待优化意见，每天凌晨增量更新。每条意见的括号明细里通常带引号包裹的违规原句，
这比静态 Excel 更适合做口径基线。

同步链路：

- `app/audit_feed.py`：分页拉取（size=200）→ `parse_reason()` 拆成
  「意见模板 / 括号明细 / 违规原句」→ upsert 到 `audit_case`（主键 `key:reason_index`）。
- `audit_sync` 记录最近同步时间与条数；服务启动时若超过 `AUDIT_FEED_SYNC_HOURS`
  （默认 12h）就在后台线程同步一次，接口不可达时静默跳过。
- `POST /api/audits/sync` 手动同步；`GET /api/audits/stats` 看条数与主要口径。
- `scripts/sync_audits.py` 供命令行/计划任务调用。

用途与边界：

- `build_prompt_block()` 取出现次数最多的 8 类拒审口径 + 近期原句，注入语义审核提示词，
  让判定口径跟得上平台变化。
- **只作口径参考，不自动生成阻断规则**。新出现的口径先体现在提示词里，要变成硬规则
  仍需人工确认，避免误报扩散。

首次同步结果（2026-11-24）：1061 条拒审记录 → 1321 条 reason → 34 类口径，
其中「夸大功效」878 条、「不良导向」154 条、「内衣入口图真人素材」83 条。

## 20. 从判例自动挖候选规则（2026-11-24）

"意见模板太粗"只说明模板不能直接变规则，不代表只能人工挑原句。

`app/rule_miner.py` 对括号里的违规原句做 n-gram 统计（2–8 字），按覆盖的
不同素材数排序，再过滤：

- 中性词 / 产品名（赘肉、脂肪、塑身衣、收腹裤…）；
- 虚词开头结尾的碎片（的/了/是/又/都…）；
- 被更长候选包含且支持度接近的碎片。

输出 `rules/candidates.json`，每条带：覆盖素材数、覆盖账户数、命中通过样本数、
精度估计、示例原句。命令：`.venv/Scripts/python.exe scripts/mine_rules.py`。

| 收腹又提臀 | 49 | 0 | 可做阻断关键词 |
| 轻松显瘦十几斤 | 26 | 0 | 可做阻断关键词 |
